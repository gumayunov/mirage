# LangGraph в miRAGe — разведка применимости

Дата: 2026-04-15
Статус: research / idea

## Вопрос

Где в miRAGe осмысленно использовать LangGraph?

## Ответ

LangGraph уместен там, где pipeline линейный сейчас, а требуется ветвление,
итерация или персистентное состояние между узлами. Для прямого
`retrieve → generate` он избыточен.

## Сценарии применения

### 1. Agentic RAG для поиска

Граф:

```
rewrite_query → retrieve (semantic + keyword) → grade_chunks
  ├── низкая релевантность → refine_query → retrieve (цикл)
  └── ок → generate_answer
```

Решает типичную проблему RAG по книгам: один запрос часто не покрывает
контекст главы; требуется переформулировка или дорасширение.

### 2. Оркестрация мульти-модельного поиска

В miRAGe уже есть поддержка нескольких embedding-моделей на проект.
LangGraph-узлы могут параллельно опрашивать индексы разных моделей,
узел-reranker сливает результаты.

Выгода появляется, когда добавятся условные ветки (например, выбор модели
по типу запроса). Без ветвлений — хватает прямых вызовов.

### 3. Индексация с self-correction

В воркере индексатора:

```
parse → chunk → embed → validate
  ├── битые/пустые чанки → retry-ветка
  └── ок → commit
```

Для текущего воркера — overkill. Обычный retry/queue покрывает случаи.

### 4. Суммаризация книги (map-reduce)

В roadmap уже есть LLM summarization (коммит `db5d8f9`).

```
split_by_chapter → parallel summarize_chunk → merge_summaries → final_summary
```

Здесь LangGraph удобен: ветвления, параллельность, накопление состояния.

## Trade-off

LangGraph добавляет зависимость и слой абстракции. Окупается только при
наличии циклов, ветвлений или shared state между узлами.

## Рекомендация

Начать с **(1) agentic retrieval** или **(4) суммаризация** — там выгода
максимальная. Остальное — не трогать, пока не появятся реальные требования
к ветвлению.
