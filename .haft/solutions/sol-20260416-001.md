# Solutions for: Scope суммаризации: parent, child или оба — и что попадает в поиск

Problem: prob-20260416-001

## Variants (3)

### V1. V1: Суммаризируем только parent, поиск по (child original + parent summary)

Parent-chunks (большие) получают summary. В embeddings таблицах хранятся: (child, original) как сейчас + (parent, summary) рядом. Search делает UNION: (a) по child original с DISTINCT ON parent_id, (b) по parent summary, каждый parent владеет своим embedding. Дедупликация по parent_id на выходе (child.parent_id == parent.id).

**Strengths:**
- LLM-вызовов в ~N_children/N_parents раз меньше (обычно 5-20x)
- Естественная семантика: parent теперь имеет две точки входа — детальное (child) и обобщённое (summary)
- Схема проще: content_type только у parent-рядов, у child всегда original
- Recall на high-level вопросах ("о чём глава") улучшается — parent summary именно про это

**Novelty:** Минимальная надстройка над существующей parent-child архитектурой — summary добавляется строго на другом уровне (parent), без смешивания content_type для одного chunk.

**Weakest link:** Запросы про конкретные детали (точная цитата, имя, дата) всё равно работают только через child original — если нужное слово не попало в child chunk, не найдём.

**Risks:**
- Нужен новый UNION в search.py (сложнее)
- Parent обычно имеет 3-5 детей, при попадании summary в топ — что показываем как content (parent? ни один child?)

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Открывает дверь к иерархической суммаризации (из research документа) — parent summary это первый уровень дерева суммаризаций (chapter/part — выше).

### V2. V2: Суммаризируем только child, поиск по child (original + summary)

Каждый child получает summary. В embeddings_<model> хранятся (chunk_id, content_type=original|summary) для child-чанков. Search ищет по обоим content_type, дедуплицирует по chunk_id (мин distance), затем DISTINCT ON parent_id. Parent не трогаем.

**Strengths:**
- Search почти не меняется (просто убираем фильтр по content_type)
- Единая семантика: chunk как был search target, так и остался
- Recall на запросах-переформулировках улучшается ("кто вошёл" vs "Алиса вошла")

**Novelty:** Точно соответствует текущей search-архитектуре (search-target = child), но добавляет второй content_type на том же уровне.

**Weakest link:** Стоимость индексации — по одному LLM-вызову на каждый child (обычно 5-20x больше чем парентов). Плюс child мал по объёму (~400 токенов) — summary от 400-токенного чанка может быть бесполезной (мало что выжимать).

**Risks:**
- В 5-20 раз больше LLM-вызовов при индексации
- Суммаризация 400-токенного текста малополезна
- Пустые summary часты (у коротких чанков нечего извлекать)

### V3. V3: Суммаризируем обоих (текущий дизайн)

И parent, и child получают summary. В embeddings хранятся 4 ряда на parent-child пару (parent+original, parent+summary, child+original, child+summary). Search ищет по всем, дедуплицирует по chunk_id, затем как-то наверх по parent (дизайн не договорил).

**Strengths:**
- Максимальный recall
- Супер-флексибельно — настраивать веса можно после замеров

**Novelty:** Покрывает все уровни, но самый затратный.

**Weakest link:** 4x стоимость индексации + 4x размер embeddings + неясная семантика search-выдачи (когда parent.summary попадает в топ — какой результат показываем?).

**Risks:**
- Большая стоимость LLM-вызовов на индексации
- Неопределённая семантика DISTINCT при parent-summary+child-summary одновременно
- Сложнее дебажить зачем-то пришёл тот или иной чанк в топ
