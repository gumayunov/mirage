# V1: Суммаризируем только parent, поиск по (child original + parent summary)

## 1. Problem Frame

**Signal:** Дизайн 03 говорит, что суммаризация идёт и для parent, и для child, и что parent-summary «тоже может попадать в поиск». Но текущая архитектура (worker.py:179-186, search.py:77) использует parent только как контекст, а search target — это child. Включение parent-summary в поиск ломает инвариант «одна точка входа на parent» (DISTINCT ON parent_id) и требует перепроектирования search.

**Constraints:**
- User сохраняет видение оригинального текста, не summary
- Нельзя ломать текущий поиск child-эмбеддингов
- Суммаризация — дорогая операция, нельзя генерить зря

**Acceptance:** Зафиксирован выбор: что суммаризируется (parent/child/оба), что попадает в embeddings, как меняется search-query, как это влияет на deduplication и на DISTINCT ON (parent_id).

## 2. Decision

**Selected:** V1: Суммаризируем только parent, поиск по (child original + parent summary)

**Selection policy:** Минимальная стоимость при явном улучшении recall для high-level запросов; предпочтение stepping-stone вариантам.

**Why selected:** Дёшево (5-20x меньше LLM-вызовов), семантически чисто (parent = обобщение, child = детали), естественно вписывается в существующую parent-child архитектуру, stepping stone к иерархической суммаризации из research.md (parent summary — первый уровень дерева).


**Invariants:**
- User видит оригинальный текст в выдаче, не summary
- Child-эмбеддинги по original сохраняются

## 3. Rationale

**Counterargument:** Если большинство реальных запросов — точные цитаты, parent-summary не даст прироста, а стоимость индексации всё равно вырастет.

**Selected variant weakest link:** Запросы с точными цитатами (имена, даты, термины) всё ещё зависят от child original; если слово не попало в child — не найдём.

**Rejected alternatives:**
| Variant | Verdict | Reason |
|---------|---------|--------|
| V1: Суммаризируем только parent, поиск по (child original + parent summary) | **Selected** | Дёшево (5-20x меньше LLM-вызовов), с�... |
| V2: только child | Rejected | Суммаризация 400-токенного чанка малополезна, в 5-20 раз дороже V1, выигрыш recall не очевиден. |
| V3: обоих | Rejected | 4x стоимость индексации и размер БД, недопроектирована дедупликация parent+child в search-выдаче. |

## 4. Consequences

**Rollback plan:**
Triggers:
- Если после замеров parent-summary не даёт recall-прироста за 3 недели
- Если стоимость индексации выросла >2x от ожидаемого
Steps:
1. Убрать SummaryWorker из indexer/__main__.py
2. Пометить parent-эмбеддинги deprecated (оставить в БД), search убрать UNION
Blast radius: Схема БД сохраняется; выключение функции без сноса таблиц.

**Affected files:** src/mirage/shared/db.py, src/mirage/indexer/worker.py, src/mirage/indexer/summary_worker.py, src/mirage/indexer/embedding_worker.py, src/mirage/api/routers/search.py, docs/designs/03-llm-summarization/design.md
